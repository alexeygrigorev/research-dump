## Talk 1 — Thu Dec 3: "You don't need a better idea. You need a smaller first version."

**Maps to:** Module 1, *Choose a problem and a small first version* (lessons: understand the task people need to complete; choose a problem and product idea; find communities and potential testers; share your progress as you build; define the first version and how to check it).

**Abstract (draft).** Most people stuck on a product don't lack ideas; they lack a first version small enough to finish and a person to put it in front of. In this talk I walk through how I choose who a product is for, pick one task it should help them complete, and write down how I'll check whether the first version does that — using a real example. You'll leave with a one-page product brief you can fill in tonight.

**Outline**
1. The pattern: idea → huge scope → no launch. (Use only Alexey's own experience; no invented statistics.)
2. Pick the user and the one task.
3. Write the first version's "done" check before building anything.
4. Where the testers come from — start looking in Module-1 week, not after building.
5. Worked example on screen (assign: Alexey's own project, or a consenting volunteer; if neither is ready, label it a hypothetical worked example).
6. Close: what the cohort does with this in Module 1; **20 seats**, application/selection; how to apply.

**Free takeaway (optional):** *Before You Build: Product Discovery Working Kit* (existing companion in bots-management README) — confirm live before linking.

## Talk 2 — Thu Dec 10: "Let AI write the code — then prove it works"

**Maps to:** Module 2, *Build and deploy the first version* (organize the project and give AI small tasks; define what screens need from the API; build backend and store data; connect the main task end to end; test changes and automate checks; deploy and write setup instructions).

**Abstract (draft).** AI can write a lot of code quickly, and you still have to know whether the main task works. I show how I give a coding assistant small, bounded tasks with the context it needs, how I check what it wrote, and how I get one path — start to finish — onto a live URL with instructions another person can follow.

**Outline**
1. Small tasks + context beat one giant prompt (demonstrate, don't assert).
2. Check the work: run the main task, not just "it compiled".
3. Tests and automated checks that protect the main task.
4. Deploy; write the setup instructions.
5. Honest limits: no prior coding is required for the course, but you must be able to install and run an AI coding assistant — say this plainly so no one self-selects wrongly.
6. Close with the standard: in the cohort, every participant submits a deployed first version for midterm review.

## Talk 3 — Thu Dec 17: "Before you show anyone: the page, the free access, and the three testers' questions"

**Maps to:** Module 3, *Prepare your product for testers* + midterm/peer-testing structure (remove features you can postpone; explain the product to a first-time user; fix problems in the main task; give reviewers free access; ask testers for useful feedback; write instructions and known limitations; test three peer products; group office-hours review).

**Abstract (draft).** The first outsider to try your product will hit problems you can't see. I show what to cut, how to explain the product to someone seeing it for the first time, how to give a reviewer free access, and how to ask for feedback that tells you something. Then I show what a review of a submitted project looks like in the cohort's group office hours.

**Outline**
1. Cut the postponable features.
2. First-time-user explanation test.
3. Reviewer access + short test instructions + known limitations.
4. The three questions you ask testers.
5. Peer testing, as the course does it: you test three products and receive feedback on yours.
6. Review a volunteer's or an anonymized project live (agree permissions first; free-talk reviews cover only 2–3 projects, not all who ask — say so).
7. Close: group reviews, no private 1:1 coaching; seats; apply.

## Talk 4 — Tue Dec 22: "They said 'add dark mode.' What did they actually do?"

**Maps to:** Module 4 (improve your product from feedback) and Module 5 (track usage and prepare to launch).

**Abstract (draft).** What testers *say* and what they *do* are different data. I show how to separate problems people hit from feature requests, decide what to fix first, track whether people complete the main task and where they stop, and check errors, hosting costs, and service limits before sharing widely.

**Outline**
1. Feedback vs. requests: sort a real feedback list.
2. Choose what to fix first; write the changelog entry.
3. Choose the one action that means "it worked for this user" and track it.
4. Where people stop; compare with what they said.
5. Errors, hosting costs, service limits — look before you launch.
6. Close: the application/waitlist status in honest numbers (only real numbers: e.g. "N applications for 20 seats" **only if true**).

**Evidence rule:** Use real data from a real product. If none exists, say it is a constructed example.

## Talk 5 — Tue Dec 29: "Launching without a big audience: where to go, what to say, what to record"

**Maps to:** Module 6 (launch and learn from the response) + final project/launch report (update how you describe the product; finish a landing page; choose where to share; write launch messages; launch and invite potential users; record the response).

**Abstract (draft).** Launch is not a big moment; it's a small, recorded attempt to put the product in front of people who might need it. I show how to explain who it's for, choose where to share, write the invitation, and record what happens — including when nothing happens.

**Outline**
1. Who it's for, in one sentence; update the product description.
2. Choose 1–3 places; write the invitation.
3. Record the response; decide the next step.
4. Honest expectation setting: customers/revenue/product-market fit are not promised (FAQ).
5. Close: **the cohort starts Mon Jan 11. 20 seats.** The final application or waitlist step and what happens after it.
